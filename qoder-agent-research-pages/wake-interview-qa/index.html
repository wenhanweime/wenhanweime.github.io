Wake 面试 QA：云端 Agent、Job Agent 与 AI 职责网络

这不是一份功能清单，而是一组可直接用于面试表达的产品判断。核心观点：Wake 不应该被讲成另一个 Coding Agent，也不应该只讲成云端版 OpenClaw/Hermes；它更应该被定义为技术组织里的可治理 AI 职责网络。

云端 Agent Job Agent AI 数字员工 工程健康 组织级治理

一组可以先抛出来的犀利观点

1. issue-to-PR 已经是基线，不是壁垒。能开 PR、能跑测试、能修简单 bug，已经被 GitHub、Codex、Cursor、Jules、Devin 拉成市场标配。
2. Task 是执行单位，Job 才是责任单位。Wake 如果只接单次任务，就会被通用 Coding Agent 夹击；它要卖的是长期负责某类工程健康结果。
3. 代码是 Wake 的训练场，不是边界。代码任务反馈快、可审核、ROI 清楚，所以适合做 wedge；但终局不是“帮工程师写代码”。
4. 云端 OpenClaw/Hermes 是底座，不是终局。云端电脑、浏览器、终端和文件系统很关键，但它只是 action runtime；上面还要有职责、治理和组织协同。
5. 真正的终局不是超级 Agent，而是 Agent Workforce。组织工作天然有分工、权限、验收、升级路径和人类 owner，单一万能 Agent 更像 demo 心智。
6. 企业买的不是自动化，而是可控的自动化。权限、审计、审批、回放、归因、回滚，比“模型更聪明”更接近 ToB 成交条件。
7. AgentOps 是门票，不是产品终点。trace、日志、eval、policy 都必须有，但 Wake 不能只卖平台；它必须绑定具体职责结果。
8. Repo maintainer 也不再是空地。Jules scheduled tasks、auto CI fixer、PR feedback iteration 已经证明这个方向有人在做，Wake 必须上升到组织级职责闭环。
9. 最强架构不是“看屏幕点按钮”。Computer-use 解决长尾工具；高频关键任务应优先走 API、CLI、MCP 和 durable workflow。
10. Wake 的第一版产品单位应是 responsibility contract。职责、触发、权限、产物、验收、指标、升级路径，比“创建一个 agent”更适合企业理解和采购。
11. Wake 不要抢 IDE cockpit。Cursor、Claude Code、Codex 已经占住开发时入口；Wake 更适合接管开发外持续 owner：CI、依赖、release、incident follow-up。
12. 差异化会从 runtime 转向组织记忆。runtime 会商品化，真正难复制的是团队规范、历史失败模式、责任地图、审批习惯和指标体系。

面试 QA

Q1你怎么一句话定义 Wake？

Wake 不是另一个 AI 助手，也不是单纯 Coding Agent；它应该是面向技术组织的可治理 AI 职责网络。

更完整地说，Wake 让团队把持续发生、跨系统、可审核、可度量的技术职责委派给一组长期运行的 AI owners，并让它们和人类团队协作交付结果。

一句话面试版：竞品大多在卖“agent 能帮你做事”，Wake 应该卖“某个持续技术职责终于有人长期负责”。

Q2Wake 和 Devin、Codex、Cursor、Claude Code 最大区别是什么？

Devin、Codex、Cursor、Claude Code 更像高能力工程执行者，擅长从一个 prompt、issue、PR 或 IDE 上下文出发完成单次工程任务。Wake 如果也这么讲，就没有清晰差异化。

Wake 应该切到另一个层级：不是“我派一个任务给 AI”，而是“团队把一个长期没人稳定负责的技术职责交给 AI owner”。例如 CI Steward、Dependency Upgrade Owner、Release Readiness Coordinator、Incident Follow-up Owner。

差异不是会不会写代码，而是谁对持续结果负责。

Q3为什么你一直强调 Task 和 Job 的区别？

因为这是 Wake 定位的底层分水岭。

维度Task AgentJob Agent
工作单位一次任务长期职责
典型问题帮我修这个 bug长期维护 main branch CI 绿色
结束条件任务完成指标持续达标
记忆价值弱，做完即散强，越做越懂团队
商业价值替人省一次时间替组织承担一类责任
Task 是执行单位，Job 是责任单位。Wake 要赢，必须从执行外包升级到责任委派。

Q4如果 Wake 最初想做云端 OpenClaw/Hermes，这个方向对吗？

方向对，而且比聊天助手、IDE 插件、普通 issue-to-PR agent 更接近下一代 agent 的底层形态。

云端 OpenClaw/Hermes 的价值在于，它把 agent 从“生成文本”推进到“操作真实工作环境”：浏览器、终端、文件、repo、CI、文档、内部系统。它也天然适合异步执行、持久 workspace、权限控制和企业审计。

但它不能停在“云端万能电脑”。那只是 action runtime，不是完整产品。

云端 OpenClaw/Hermes 是 Wake 的发动机，不是 Wake 的车。

Q5那下一代 Agent 的“终局形态”是什么？

我不认为终局是一个无所不能的单体超级 Agent。更现实的终局是 Agent OS + Agent Workforce。

也就是：底层有云端 runtime，可以操作浏览器、终端、文件和工具；中间有 durable execution、memory、MCP/A2A、eval、observability、policy；上层是面向组织的岗位和职责，能被授权、被审计、被评估、被升级。

未来不是“一个 Agent 替代所有人”，而是“一组可治理 AI 岗位进入组织分工”。

Q6当前最值得学习的开源 Agent 架构是什么？

如果只选一个组合，我会看 LangGraph + OpenHands。

LangGraph 代表长期、有状态、可恢复、可插入人工审批的 agent workflow。OpenHands 代表软件工程 agent 的真实执行环境，包括代码、终端、浏览器、测试和云端扩展。再叠加 MCP、长期记忆、policy、observability，才接近 Wake 需要的底座。

Letta/MemGPT 值得看长期记忆，CrewAI 值得看 role-based team 心智，SWE-agent 值得看 agent-computer interface 和评估方式，但它们都不是单独终局。

开源里不要找“一个最强 Agent”，要拼出一套生产级 agent stack。

Q7闭源产品里你最看重谁？

我会拆开看：

  • Claude Code：terminal-first、项目上下文、工具调用和 coding loop 很强。
  • Codex / ChatGPT Agent：cloud sandbox、多入口、审批和安全边界值得学。
  • Devin：AI software engineer 和 agent fleet 的心智最强。
  • Cursor：IDE + background agents + Bugbot，把开发者日常入口抓得很牢。
  • Jules：GitHub-native async maintainer，已经直接打到 repo maintenance。
  • Manus：证明 cloud computer-use 心智成立，但也暴露通用云端 agent 太宽、太难解释 ROI。
Wake 不该复制其中某一个，而要把强 runtime、组织职责和治理控制面组合起来。

Q8为什么 Wake 第一阶段应该从代码和工程健康切入？

因为代码是最适合证明“AI 可以承担持续职责”的场景。

代码有编译、测试、CI、diff、review comment、PR、rollback，这些都天然可验证。企业也更容易接受一个 AI 先读 repo、看 CI log、开 draft PR，而不是直接操作客户数据、财务系统或生产数据库。

但代码只是训练场。Wake 的最终边界不应该是写代码，而应该是 engineering responsibilities：CI、依赖、release、incident、security remediation、engineering knowledge。

代码是最早能闭环的责任域，不是 Wake 的天花板。

Q9Wake 的 MVP 应该做什么？

我会从 Team CI Steward 或 Repo Reliability Engineer 切。

它的 responsibility contract 可以这样定义：

  • 职责：维护 main branch CI 绿色。
  • 触发：CI failure、PR failure、scheduled scan。
  • 权限：读 repo 和 CI log，开 branch 和 draft PR，不能直接 merge。
  • 产物：diagnosis、fix PR、test evidence、risk label、rollback note。
  • 指标：MTTR、自动修复率、review 通过率、复发率、节省的人类时间。
第一版不要做“创建任意 Agent”，而要做一个窄到能被衡量的岗位。

Q10Wake 用户到底是谁？

Wake 的用户不是单点个人，而是四层人：

层级角色诉求
直接操作者工程师、Tech Lead、SRE、QA、AppSec把低价值、重复、跨系统的工程任务交出去
责任拥有者EM、研发负责人、平台负责人看 Wake 是否改善团队指标
实施者Platform、DevEx、Developer Productivity把 agent 标准化接入工程平台
审批者Security、IT、Legal、Compliance控制权限、数据、审计和风险
Wake 不是卖给一个工程师的玩具，而是进入技术组织分工体系的基础设施。

Q11为什么组织协同比单 Agent 能力更重要？

因为组织里的工作从来不是一个目标、一个权限、一个上下文、一个评价标准。它涉及 owner、reviewer、approver、escalation contact，也涉及不同系统里的事实来源。

多 agent 协作本身不稀奇，容易变成噱头。真正有价值的是：每个 agent 有清晰职责边界，有共享但不污染的上下文，有主责 agent 负责最终结果，有人类在关键节点审批，有完整 audit trail。

多 Agent 的价值不在数量，而在责任、权限、上下文和验收能被组织化。

Q12Wake 应该怎么避免和内部 Code Work / Work / Jarvis 打架？

边界应该按工作单位和责任归属切，而不是按“能不能写代码”切。

Code Work 更偏开发时工具和单次工程执行，Work/Jarvis 更偏个人或通用办公任务。Wake 应该占住组织级、长期、可度量、可治理的岗位职责。它可以调用 Code Work、OpenClaw/Hermes 或其他 runtime，但自己的产品抽象必须是 responsibility contract 和 control plane。

Wake 不抢执行入口，Wake 抢责任归属。

Q13企业为什么会为 Wake 付费？

企业不会长期为“看起来很聪明”付费，只会为可控的结果付费。

Wake 的付费理由应该来自几个可量化指标：CI MTTR 下降、依赖 backlog 清空、release delay 减少、incident action items 闭环、review load 降低、senior engineer 被打断次数减少。

如果能证明一个 Wake owner 长期负责一类脏活，并稳定改善团队指标，它的钱就不只来自软件预算，还可能来自人力效率预算和平台工程预算。

不要卖“AI 很强”，要卖“这个责任以前没人负责，现在有了 owner，而且指标变好了”。

Q14Wake 最大风险是什么？

最大风险不是模型不够强，而是产品定位滑成“又一个通用 Agent 工作台”。

如果 Wake 什么都能做，最后用户会不知道为什么买、该让谁买、怎么衡量成功。另一个风险是只做 runtime 或 AgentOps，变成底层工具，被 LangGraph、OpenHands、MCP 生态、云厂商和开源框架持续压价。

Wake 的危险不是做小，而是做宽以后失去责任锚点。

Q15如果面试官问你会怎么做产品路线图？

我会分三阶段：

  1. 单一职责做深：先做 Team CI Steward，把诊断、低风险修复、draft PR、证据、审批和指标跑通。
  2. 复制到相邻职责：扩展到 Dependency Owner、Flaky Test Investigator、Release Readiness Coordinator。
  3. 形成职责网络：做 Responsibility Map、Agent Team View、Org-level Governance & Metrics，让 Wake 从单岗位变成技术组织的 AI responsibility network。
路线图不是从更多能力开始，而是从一个最窄责任闭环开始。

Q16你最后会给 Wake 一个什么定位？

Wake is a governed AI responsibility network for technical organizations.

中文就是：Wake 是面向技术组织的可治理 AI 职责网络，让团队把持续发生、跨角色、跨系统、可审核、可度量的技术职责委派给长期运行的 AI owners，并让它们和人类团队协作交付结果。

面试收束句：Wake 不应该成为“云端万能助手”，而应该成为技术组织里第一个真正可被授权、被约束、被评估、被复盘的 AI 同事体系。
